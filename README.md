# week_4-day_1

## Student API

Student records use the datasource configured by the active Spring profile and remain available according to that database's persistence configuration. On first startup, the application inserts sample records if the database is empty.

The CRUD endpoints are:

- `GET /api/students?page=0&size=10&name=rah` lists students with optional case-insensitive name filtering and pagination.
- `GET /api/students/{id}` reads one student.
- `POST /api/students` creates a student with `name` and `email`.
- `PUT /api/students/{id}` updates a student's `name` and `email`.
- `DELETE /api/students/{id}` deletes a student.

Student IDs are generated by the database. Request bodies require a 2-to-50 character name and a valid email address. Email addresses must be unique.

## Interactive API Docs

Run the app with `mvnw.cmd spring-boot:run`, then open [Swagger UI](http://localhost:8081/swagger-ui/index.html). The OpenAPI document is available at `http://localhost:8081/v3/api-docs`. Reads are public. Creating, updating, and deleting students require HTTP Basic authentication.

The dev profile uses `student-writer` / `local-demo-password` for local demonstrations. Override these with `STUDENT_API_USER` and `STUDENT_API_PASSWORD`. When running with the `prod` profile, both environment variables are required; do not reuse the development credentials in a deployed environment.

## CRUD Demo (PowerShell)

With the app running on port 8081, run the following in PowerShell. These commands create a record, read it, update it, and delete it:

```powershell
$base = "http://localhost:8081/api/students"
$pair = "student-writer:local-demo-password"
$headers = @{ Authorization = "Basic " + [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes($pair)) }
$body = @{ name = "Taylor Reed"; email = "taylor@example.com" } | ConvertTo-Json

$created = Invoke-RestMethod -Method Post -Uri $base -Headers $headers -ContentType "application/json" -Body $body
$created

Invoke-RestMethod -Method Get -Uri "$base/$($created.id)"

$updatedBody = @{ name = "Taylor Morgan"; email = "taylor.morgan@example.com" } | ConvertTo-Json
Invoke-RestMethod -Method Put -Uri "$base/$($created.id)" -Headers $headers -ContentType "application/json" -Body $updatedBody

Invoke-RestMethod -Method Delete -Uri "$base/$($created.id)" -Headers $headers
```

## Build and Test

Use the Maven Wrapper from the project root on Windows:

```powershell
./mvnw.cmd clean test
./mvnw.cmd verify
./mvnw.cmd spring-boot:run
```

`clean` removes generated output, `test` compiles and runs the JUnit suite, and `verify` runs the configured Maven lifecycle through its verification phase. Useful focused commands:

```powershell
./mvnw.cmd -Dtest=StudentServiceTest test
./mvnw.cmd -Dtest=StudentControllerTest,ApiSecurityTest test
./mvnw.cmd dependency:tree
./mvnw.cmd -U test
```

If dependency resolution fails, check network/proxy and repository access first, then inspect `dependency:tree` for version conflicts. `-U` refreshes Maven's cached snapshots and releases. `-o` is useful only when all required artifacts are already cached. Avoid `-DskipTests` or `-Dmaven.test.skip=true` for a verification build because they hide test failures; the latter also skips test compilation.

The Maven lifecycle progresses through phases such as `validate`, `compile`, `test`, `package`, `verify`, and `install`. Running a later phase runs the earlier phases first. `package` creates the artifact; `verify` additionally runs configured verification checks.

## Test Coverage

- **Unit tests:** `StudentServiceTest` uses Mockito to isolate pagination bounds, blank and trimmed filters, persistence/notification order, and missing-student update/delete behavior.
- **Controller/API tests:** `StudentControllerTest` uses standalone MockMvc to check JSON validation, malformed bodies, pagination boundaries, CRUD status codes, and not-found responses.
- **Integration tests:** `StudentRepositoryTest` uses the JPA test slice and an embedded database; `ApiSecurityTest` starts the Spring context and checks HTTP Basic, OpenAPI exposure, validation, and duplicate-email conflict behavior.

Database and framework integrations should have focused slice or integration tests; keep fast service logic tests isolated with mocks. Each test should assert observable behavior (status/body or repository interaction), including error and boundary cases, rather than only asserting that a method ran.

## SQL and Query Performance Notes

The student API currently uses single-table queries; it does not need a join. `StudentRepository` pages records ordered by `id` and filters names using `findByNameContainingIgnoreCase`. The primary key indexes `id`, and the unique email constraint also provides an index for email lookups and duplicate prevention.

The contains search is effectively a case-insensitive pattern like `LOWER(name) LIKE '%term%'`. A leading wildcard and a function around the column generally prevent a normal B-tree index from narrowing the search, so the database may scan many rows. A simple optimization for prefix search is `LOWER(name) LIKE 'term%'` with a matching functional index where the database supports it; if arbitrary substring matching is required at scale, choose a database-specific full-text/trigram index. Confirm with that database's `EXPLAIN` before adding indexes, since index syntax and planner behavior vary. Keep pagination bounded, and select only needed columns if responses grow beyond the current small DTO.

Use a transaction when a multi-step operation must be atomic. Repository methods provide their own transaction boundaries, but a read-modify-save workflow may need a service-level `@Transactional` boundary if concurrent updates must be consistent. The POST path saves the student and then sends a notification; a notification failure can occur after persistence, so production delivery should use an outbox/retry design if the two effects must not diverge.

## JVM, Logging, and Debugging Notes

- **Heap:** stores objects. An `OutOfMemoryError: Java heap space` often means excessive retention or unbounded collections; inspect a heap dump and allocation profile before increasing `-Xmx`.
- **Stack:** each thread's call frames and local execution state. Deep or unbounded recursion commonly causes `StackOverflowError`; inspect the repeating stack frames and fix the recursion/base case.
- **Metaspace:** stores class metadata outside the Java heap. `OutOfMemoryError: Metaspace` can indicate many dynamically generated classes or a class-loader leak; inspect class-loading/class-unloading and class-loader references.
- **Garbage collection:** reclaims unreachable heap objects. Frequent long pauses or high GC time suggest allocation/retention pressure; compare GC logs and heap usage before tuning collector flags.

For a reproducible API failure, run the focused test first, then reproduce through Swagger/curl and compare the HTTP status/body with the application stack trace. In VS Code, set a breakpoint in the controller/service and inspect the request DTO and exception cause. Use structured logging with request context; never log passwords, authorization headers, or database credentials. Configure package log levels with `logging.level.<package>=DEBUG` only temporarily when diagnosing.

For performance measurement, establish a baseline and repeat the same request/data size before and after a change. Big-O gives a growth estimate: a full scan is typically `O(n)`, indexed equality lookup is typically `O(log n)` for a B-tree, and sorting `n` rows is commonly `O(n log n)`; real latency also depends on I/O, cache state, row width, and query plans. Avoid claiming an optimization without comparing plans and measurements.
